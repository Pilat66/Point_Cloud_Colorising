# z-buffer

При раскрашивании с помощью z-buffer 0.3 стволы деревьев раскрашиваются с невидимой
стороны до глубины буфера. Поэтому выбирать z-buffer лучше с параметрами:

```
--occlusion-depth-tol 0.03
--occlusion-cell 1
```

# Проекция

- Собственная векторная проекция pinhole (radtan/plumb_bob, до 5 коэффициентов)
  в ~20 раз быстрее `cv2.projectPoints` в Python (514 → 25 мс на 72k точек × 19
  кадров), расхождение с OpenCV ≤ 0.0025 px. В C++ выигрыша по wall-времени нет
  (в пределах шума).
- `cv2.fisheye.projectPoints` в Python требует массив формы (N,1,3): форма (N,3)
  даёт assertion OpenCV 5.0 (до итерации ITER-20260917-161918 fisheye-путь
  Python падал всегда).
- Гейты по углу и дистанции применяются ДО проекции (Pass 1), поэтому конус
  `--max-view-angle` экономит 0–12 % проекций (на плоских фикстурах — 0 %).
- Реальные узкие места прогона: `cv2.imread` (~35 мс на кадр 1600×1300) и
  проекция; близость `‖pc‖` считается для гейта и практически бесплатна.


# Кубовый режим (ColoriseMap --cube)

- Карта 43-56 млн точек в кадровом конвейере требует ~20 ГБ RSS: 8 потоков
  держат массивы размером с кадр (~30 млн точек × 44 Б) плюс ожидающие коммита
  результаты. Кубовый режим обходится ~2 ГБ: точки хранятся исходными int32
  (12 Б) + gps_time (8 Б) + intensity (2 Б), промежуточные массивы кадра не
  создаются.
- Занятие из файла: gps_time лежит в LAS-записи по смещению 20 (форматы 1/3/4/5)
  или 22 (форматы 6-10); в point format 7 RGB занимает байты 30-35, и запись RGB
  по смещению 28 затирает gps_time (получаются NaN).
- Сетку минимума глубины (z-буфер) нельзя наполнять из нескольких потоков одной
  общей сеткой: `if (z < zmin[c]) zmin[c] = z;` теряет обновления и результат
  становится недетерминированным. Нужны приватные сетки на поток и
  детерминированное слияние.
- Для карты с 258 кадрами и подвыборкой 2 млн точек прогон занимает ~28 с и
  155 МБ RSS; окклюзия (cell=1, tol=0.03) отсеивает ~6.5 % точек, без неё
  окрашивается 100 %.


# Производительность кубового режима

- Локальность важнее арифметики: хранение точек пятью отдельными массивами
  (X, Y, Z, gps_time, intensity) при обходе куба даёт ~4 промаха кэша на точку.
  Упаковка в одну запись 24 Б в порядке кубов ускорила полный прогон 56 млн
  точек с 4:57 до 1:26 (при том же результате).
- Потоки: статическое разбиение кубов по потокам даёт перекос (плотность кубов
  разная) — на 8 ядрах было занято ~4. Динамическая выдача блоков по 64 куба
  через атомарный счётчик + приватные сетки z-буфера сохраняют детерминизм.
- Чтение LAS двумя потоковыми проходами (счёт кубов, затем упаковка) вместо
  хранения «сырых» массивов экономит ~1.2 ГБ на 56 млн точек и стоит ~5 с.
- В LAS-писателе нельзя материализовать список индексов выводимых точек:
  на 56 млн точек это 450 МБ (заметно на фоне 2 ГБ общего пика).
- Запись в LAS нужно проверять после каждого write: при переполнении диска файл
  молча получается обрезанным (наблюдалось на 646 МБ вместо 2 ГБ).
