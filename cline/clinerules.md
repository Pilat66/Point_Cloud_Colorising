# Project Development Protocol — Point_Cloud_Colorising

Правила работы агента в этом репозитории: ROS-пакет `point_cloud_projection`,
ROS-free C++ порт `colorise/` и Python-инструменты раскраски облака точек.
Сначала — специфика проекта (§1–§4), затем общий процесс: итерации, CHANGELOG,
коммиты.

---

## 1. Специфика проекта

### 1.1 Компоненты

| Компонент | Что это | Где |
|---|---|---|
| ROS 1 catkin-пакет `point_cloud_projection` | ноды `ColoriseScan` (раскраска сканов) и `ColoriseMap` (раскраска карты), общее проекционное ядро `projectAndSample` | `src/`, `include/`, `launch/`, `configs/`, `package.xml`, `CMakeLists.txt` |
| ROS-free C++ порт | тот же конвейер без ROS: гейты по дистанции/углу/краю, проекция pinhole/fisheye, z-буфер окклюзии, усреднение цвета по кадрам, `--jobs N` | `colorise/` |
| Python-версия (эталон паритета) | `colorise_offline.py` — офлайн-раскраска; `align_brightness.py` — выравнивание яркости серии фото | корень репозитория |
| Docker-окружение | сборка и запуск ROS-части (noetic) | `Docker/Dockerfile`, `Docker/run_dev.sh` |

Все три реализации раскраски (`src/colorise.cpp`, `colorise/`,
`colorise_offline.py`) воспроизводят один и тот же конвейер. Правка
проекционного ядра затрагивает их все: синхронизируй реализации и проверь
паритет (§3) либо явно сообщи пользователю, что синхронизация не требуется.

### 1.2 Ключевые инварианты

- **Побайтовый паритет C++ ↔ Python.** `colorise/build/colorise_offline` и
  `python3 colorise_offline.py` с одними и теми же флагами дают побайтово
  одинаковый PCD/LAS и идентичные строки лога по кадрам. Проверено на облаке
  1 201 612 точек и 82 кадрах (источник: `colorise/README.md`). Расхождение —
  это ошибка, а не «допустимое отличие реализаций».
- **Упаковка цвета.** В PCD `rgb` — `uint32` в PCL-соглашении:
  `(R << 16) | (G << 8) | B`. В LAS 8-битные компоненты пишутся как `v * 257`.
  Округление — half-to-even (`np.round` / `std::nearbyint`).
- **Экстраинсики по схеме `A_from_B`.** `T_camera_lidar` означает
  «camera from lidar» и применяется как есть; `T_lidar_camera` инвертируется
  автоматически. Направление автоопределяется по имени ключа и может быть
  задано явно (`--extrinsic-direction`).
- **Диалекты конфигов разные, путать нельзя.** `configs/calibration.yaml` —
  OpenCV FileStorage с обязательным заголовком `%YAML:1.0` в первой строке.
  `configs/config.yaml` — обычный YAML для yaml-cpp: добавлять в него заголовок
  `%YAML:1.0` запрещено (этот парсер его не прочтёт).
- **Топики и кадры.** Выход ROS-нод — `/colorised_points` в кадре лидара
  `os_sensor`. Компенсация рассинхронизации камер и лидара —
  `compensation_mode: none | imu | odom`.

### 1.3 Публичные интерфейсы

Публичный интерфейс проекта — CLI-флаги `colorise_offline` (C++ и Python), ключи
`configs/config.yaml`, аргументы `launch/*.launch`, имена входных файлов по
умолчанию и путь к бинарнику `colorise/build/colorise_offline`.

Не переименовывай и не меняй семантику этих элементов без явного разрешения
пользователя: они зафиксированы в README.
При изменении поведения или флагов обновляй соответствующий README:
`README.md` (EN, ROS-пакет), `colorise_offline_README.md` (RU),
`colorise/README.md` (RU).

## 2. Сборка, запуск, окружение

### 2.1 ROS-часть — только в Docker

На этой машине стоит ROS 2 Jazzy (`/opt/ros/jazzy`), инструментов ROS 1 нет,
поэтому пакет `point_cloud_projection` на хосте не собирается. Сборка и запуск
ROS-нод — в контейнере: база `Docker/Dockerfile`
(`amd64/ros:noetic-perception-focal`), вход — `Docker/run_dev.sh` (ожидает
дерево `<ws>/src/point_cloud_projection`).

```bash
catkin_make --pkg point_cloud_projection   # внутри noetic-окружения
roslaunch point_cloud_projection ColoriseScan.launch
roslaunch point_cloud_projection ColoriseMap.launch
rosbag play <bag>
```

`docker build`, `rosbag play` и любая установка пакетов — только по явному
запросу пользователя.

### 2.2 Standalone C++ (`colorise/`)

```bash
cmake -S colorise -B colorise/build -DCMAKE_BUILD_TYPE=Release
cmake --build colorise/build -j4
```

C++17, Release (`-O3`) по умолчанию. Зависимости: Eigen3, OpenCV 4, yaml-cpp,
Threads; `nlohmann/json` — vendored в `colorise/third_party/`. На этой машине
проверены OpenCV 4.6.0, yaml-cpp 0.8.0, Eigen 3.4.0. Артефакт —
`colorise/build/colorise_offline` (каталог `build/` не в git).

### 2.3 Python

```bash
. .envrc                                            # = source venv/bin/activate
python3 colorise_offline.py --output coloured.pcd
python3 align_brightness.py data/1 --stat top25
```

Проверено на Python 3.12.3, numpy 2.5.3, opencv-python 5.0.0.93, PyYAML 6.0.3,
scipy 1.18.1, laspy 2.7.0; список зависимостей — `requirements.txt`. `scipy`
нужен только для радиусного кадрирования (`--max-range`), `laspy` — только для
`.las`.

## 3. Валидация изменений

Минимальный smoke-прогон (облако `1788882799423559018.pcd`, ~24 МБ, данные —
`data/`), обе реализации с одними флагами:

```bash
venv/bin/python colorise_offline.py \
    --cloud 1788882799423559018.pcd --photos data \
    --trajectory data/trajectory.csv --camera data/camera.yaml \
    --calib data/calib.json --output /tmp/coloured_py.pcd

./colorise/build/colorise_offline \
    --cloud 1788882799423559018.pcd --photos data \
    --trajectory data/trajectory.csv --camera data/camera.yaml \
    --calib data/calib.json --output /tmp/coloured_cpp.pcd
```

Проверка паритета после правки ядра:

```bash
cmp /tmp/coloured_py.pcd /tmp/coloured_cpp.pcd   # ожидается полное совпадение
```

Плюс сверка логов: строки по кадрам (`coloured=`, `cand=`, `uniq_so_far`)
должны совпадать построчно.

Полные прогоны по данным в сотни мегабайт (`data/all_raw_points.*`, корневые
`*.pcd`) и проверка ROS-нод с `rosbag play` без явного запроса не выполняются —
это долгие и тяжёлые операции.

## 4. Данные и игнорируемые артефакты

Данные и сгенерированные артефакты в репозиторий не входят (см. `.gitignore`),
но и не удаляются самовольно:

- `data/` — тестовый набор (~1.2 ГБ): `all_raw_points.pcd`/`.las`,
  `trajectory.csv`, `camera.yaml`, `calib.json`, каталоги фото `1/`, `img-all/`.
  Это источник данных для прогонов, а не источник истины о коде; читать только
  при необходимости.
- `2026-09-08-18-56-45/` — запись прогона: mcap, датасет, результаты раскраски.
- корневые `*.pcd` (~780 МБ, включая `coloured.pcd`) и копия бинарника
  `/colorise_offline` — артефакты прогонов.
- `venv/`, `__pycache__/`, `build/`, `colorise/build/`, `PCD/` — окружение и сборка.

Правила:

- не коммить данные и артефакты; `.gitignore` не обходится через `git add -f`;
- не удалять, не «чистить» и не перемещать их без явного запроса пользователя;
- не считать содержимое этих каталогов частью исходного кода при анализе.

## Git Iteration Protocol

Значимой считается любая задача, завершающаяся коммитом.
Каждая значимая задача является отдельной итерацией.
Под итерацией понимается:
- новая функциональность;
- исправление ошибки;
- рефакторинг;
- изменение архитектуры;
- изменение конфигурации;
- изменение документации;
- обновление `CHANGELOG.md`.

Нельзя объединять несколько независимых задач в одну итерацию.

---

## Iteration Tracking (Act Mode)

При работе в режиме Act (выполнение изменений) соблюдай следующий протокол:

### 1. Начало итерации

Перед началом выполнения:
- Сгенерируй уникальный идентификатор в формате `ITER-YYYYMMDD-hhmiss` (например, ITER-20260701-120101).
- Проверь, что нет незакоммиченных изменений: выполни `git status`. Если есть - сообщи пользователю и предложи решить, что с ними делать. Если рабочее дерево не чистое - не выполнять изменения до решения пользователя.
- **Важно:** Хэш коммита не сохраняется в YAML-файле итерации. Файл описывает задачу и изменения, а не фиксирует ссылки.
- Создай YAML-файл итерации в папке `cline/iterations/YYYY-MM-DD/`:
  ```yaml
  # ITER-YYYYMMDD-hhmiss
  ---
  meta:
    id: ITER-YYYYMMDD-hhmiss
    status: started  # started | completed
    date_started: YYYY-MM-DD HH:MM:SS
    date_completed: null
    branch: <текущая ветка>

  request: |
    <полный текст запроса пользователя>

  description: null  # будет заполнен после выполнения

  changes: []  # будет заполнен после выполнения

  dependencies: []  # будет заполнен после выполнения

  notes: null  # будет заполнен после выполнения
  ```

   - Дополни `CHANGELOG.md` (корень проекта) записью об итерации: дата, секция версии/`[Unreleased]`, список изменений. Помни: `CHANGELOG.md` агентом автоматически не читается — запись ведётся всегда, чтение только по запросу пользователя.

### 2. Выполнение изменений

Выполняй все необходимые изменения в рамках итерации:
- Создавай, редактируй, удаляй файлы.
- Запускай команды в терминале: сборка (§2), smoke-прогоны и сверка паритета (§3).
- Не исправляй ошибки, не связанные непосредственно с выполненной задачей, без разрешения пользователя.
- Не выполняй автоматическое форматирование файлов, не связанных с задачей.
- Перед созданием нового класса ищи похожий класс, функцию, сервис. При обнаружении получай разрешение пользователя. Если существующая реализация решает ту же задачу с небольшими изменениями - предложи её использование.
- Перед созданием нового файла найди существующую реализацию. Если существует функционально близкая реализация — оцени возможность её расширения и сообщи пользователю.
- Не создавай дубли классов, функций, констант, конфигураций, утилит, если существует функционально эквивалентная реализация.
- Если изменение выходит за рамки пользовательского запроса — сначала получить подтверждение.
- Не удалять существующую реализацию только потому, что она кажется неиспользуемой. Удаление допустимо лишь при наличии явных подтверждений (например, отсутствия ссылок и согласия пользователя).
- Поддерживай YAML-файл итерации в актуальном состоянии. Обновляй его по мере необходимости и обязательно перед завершением итерации.
- Перед `git add` проверь `git status`: в индекс не должны попадать данные и артефакты из §4.

**Важно:** Все изменения выполняются последовательно, но **без промежуточных коммитов**.

### 3. Фиксация итерации (один коммит)

После завершения ВСЕХ изменений в рамках итерации:

1. **Обнови YAML-файл итерации**:
   ```yaml
   meta:
     id: ITER-YYYYMMDD-hhmiss
     status: completed
     date_started: YYYY-MM-DD HH:MM:SS
     date_completed: YYYY-MM-DD HH:MM:SS
     branch: <текущая ветка>

   plan: |
     <полный текст обсуждения задания в Plan Mode>

   request: |
     <полный текст запроса пользователя>

   description: <краткое описание выполненной работы>

   changes:
     - action: created
       file: path/to/file1
       description: что создано и зачем
     - action: modified
       file: path/to/file2
       description: что изменено
     - action: deleted
       file: path/to/file3
       description: почему удалено

   dependencies:
     - package@version

   notes: <дополнительные примечания>
   ```

2. Выполни `git add .` (или точечно добавь только изменённые файлы, если пользователь просил). Данные и артефакты из §4 в индекс попадать не должны.

3. Создай **ОДИН** коммит с сообщением в формате:
   ```
   [ITER-YYYYMMDD-hhmiss] <type>: <краткое описание задачи>

   <детальное описание всех изменений>

   Iteration: ITER-YYYYMMDD-hhmiss
   ```
   Где `<type>` - один из: `feat`, `fix`, `refactor`, `docs`, `test`, `perf`, `chore`.

4. В теле коммита (после пустой строки) **обязательно перечисли все изменения** в виде маркированного списка:
   ```
   Changes:
   - Created: path/to/file1 (описание, зачем создан)
   - Modified: path/to/file2 (что именно изменено)
   - Deleted: path/to/file3 (причина удаления)
   - Dependencies: added package-name (версия)
   - CHANGELOG: обновлён CHANGELOG.md
   ```

**Пример полного сообщения коммита:**
```
[ITER-20260914-220101] fix: привёл гейт max_view_angle в C++ порту к Python-версии

Changes:
- Modified: colorise/src/project.cpp (гейт по полууглу приведён к Python-версии)
- Modified: colorise/README.md (описано поведение гейта)
- CHANGELOG: обновлён CHANGELOG.md

Iteration: ITER-20260914-220101
```

### 4. Отправка изменений

После завершения всех действий отправь изменения в удалённый репозиторий по явному запросу пользователя:
```bash
git push origin <branch>
```

## Управление конфликтами в процессе Act

Если во время выполнения изменений возникают ошибки (синтаксические, логические, ошибки выполнения команд):
1. Немедленно остановись и сообщи пользователю:
   - Что пошло не так.
   - Какие файлы затронуты.
   - Предложи варианты решения (исправить вручную, продолжить с изменениями, прервать итерацию).
2. Не пытайся исправить ошибку без явного разрешения пользователя.

---

## Восстановление после сбоя

Если итерация была прервана (ошибка, отключение, ручная остановка):
1. Проверь наличие YAML-файла итерации в `cline/iterations/YYYY-MM-DD/ITER-YYYYMMDD-hhmiss.yaml`.
2. Если файл существует и `status: started`:
   - Прочитай файл, чтобы восстановить контекст.
   - Спроси пользователя: продолжить итерацию или откатиться до последнего коммита.
3. Если файла нет - предложи создать новую итерацию.

## Git Commit Rules

После завершения каждой итерации создай **ОДИН** git commit (все изменения итерации в одном коммите).

Сообщение коммита:
```text
[ITER-YYYYMMDD-hhmiss] <type>: <краткое описание>

<детальный список изменений>

Iteration: ITER-YYYYMMDD-hhmiss
```

Язык сообщения — русский (как в истории репозитория); тип — conventional commits.

Допустимые типы:
- feat
- fix
- refactor
- docs
- test
- perf
- chore

В коммит не должны попадать данные и артефакты из §4; `.gitignore` не обходится
через `git add -f`.

---

## Commit Report

После создания коммита выведи:
- iteration_id (ITER-YYYYMMDD-hhmiss);
- изменённые файлы;
- обновлён ли `CHANGELOG.md`;
- краткое описание изменений.
При невозможности выполнить действие сообщи причину и не выдумывай результат.

## General Rules

- Не удаляй пользовательский код без явного указания.
- Не выполняй массовый рефакторинг без запроса.
- Не изменяй архитектурные принципы проекта без явного разрешения пользователя.
- Перед добавлением зависимости найди возможность использовать уже существующие библиотеки проекта.
- Если информации недостаточно - задай вопрос вместо предположений.
- Главное правило: Любое изменение должно быть трассируемо: User request → Iteration → Code → CHANGELOG → Git commit
- Любое значимое утверждение о проекте должно быть проверяемым через исходный файл-источник.
- Если изменение затрагивает значительную часть проекта или более 10 файлов, агент сначала должен составить план и показать его пользователю для утверждения.
- Не меняй стиль кода, если это не требуется задачей.
- Не обновляй версии зависимостей, если пользователь этого не просил.
- Не изменяй публичные интерфейсы без явного разрешения пользователя.
- Не переименовывай файлы, классы, функции, если это не требуется задачей.
