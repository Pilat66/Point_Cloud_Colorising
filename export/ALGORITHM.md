# Алгоритм кубовой раскраски карты

Ссылки даны на файлы этого экспорта. Точка входа —
`src/ColoriseMap/cube_colourise.cpp:149` (`runCubeColourise`), вызов —
`src/ColoriseMap/main.cpp:740` (`runCube`) при `--cube > 0`.

Общая идея: карта уже построена и неподвижна, движется только камера. Значит,
для каждой точки можно независимо решить, какой снимок её «лучше» видит, не
перебирая на каждый кадр всю карту и не создавая массивов размером с кадр.

## Этап 0. Входные данные

| Что | Кто читает | Функция |
|---|---|---|
| Интринсики камеры | блок `camera` в `--calib` | `loadCameraFromCalib`, `src/colorise/src/io.cpp:233` |
| Экстраинсик камера↔лидар | тот же JSON, ключи `T_camera_lidar`/`T_lidar_camera` (авто-направление) | `loadCalib`, `io.cpp:328` |
| Позы лидара | `--trajectory` CSV (`;` или `,`, 7 колонок Эйлер / 8 кватернион) | `loadTrajectory`, `src/colorise/src/trajectory.cpp:152` |
| Снимки | каталог `--photos`, время из имени файла | `listPhotos`, `io.cpp:1097`; `photoTimestampFromName`, `io.cpp:1076` |

Поза лидара интерполируется на время снимка (`Trajectory::sampleAt`,
`trajectory.cpp:98`: линейно по позиции, SLERP по кватерниону), затем
`T_cam_from_world = (T_world_lidar · T_lidar_cam)⁻¹`
(`cube_colourise.cpp:212‑213`).

Ограничение режима: **только pinhole** (`cube_colourise.cpp:157‑159`).

## Этап 1. Два потоковых прохода по LAS

`streamLasRaw` (`io.cpp:884`) отдаёт точки чанками, поэтому «сырые» массивы на
всю карту в памяти не держатся:

1. проход 1 (`cube_colourise.cpp:180‑193`) — только считает точки по кубам:
   `unordered_map<cubeKey, count>`;
2. ключи сортируются (`:233`) → массив `keys` задаёт **детерминированный**
   порядок кубов, по нему строится CSR-индекс `start[]` (`:240‑242`);
3. проход 2 (`:246‑264`) — раскладывает точки по кубам в **упакованные** записи
   `LasPacked` (`colorise.h:154`): `gps_time` (double) + `X/Y/Z` (int32) +
   `intensity` (uint16) = 24 Б. Точки одного куба лежат подряд, поэтому обход
   куба — последовательный доступ к памяти.

Ключ куба (`cube_colourise.cpp:123‑131`): индекс по каждой оси
`floor(coord / cube) + 2²⁰`, сжатый в 21 бит, итого 63 бита
`(ix << 42) | (iy << 21) | iz`. Сцена ограничена ±1 км при кубе 1 м.

Итог: пик памяти ∝ числу точек карты (24 Б/точка), а не числу точек × кадры.
Координаты и время — исходные int32/double, поэтому при записи они
переносятся bit-exact.

## Этап 2. Кадры, для которых есть поза

Для каждого снимка, попавшего в интервал траектории с точностью
`--time-tolerance`, считаются (`cube_colourise.cpp:203‑225`):

- `Tcw` — camera-from-world,
- `c` — центр камеры в мире (столбец трансформации `Twc`),
- `axis = R_wc.col(2)` — оптическая ось камеры в мире.

Снимки без позы молча пропускаются: в лог идёт `[frames] N usable of M photos`.

## Этап 3. Отбор кубов в конусе кадра

`cube_colourise.cpp:316‑336`, параллельно по кубам (`parallelChunks`):

- центр куба `centres[i]` (из декодированного ключа, `:268‑273`);
- `d = centre − c`, `dist = |d|`;
- **радиусы**: `dist + halfdiag < --min-camera-dist` → мимо;
  `--map-max-range > 0` и `dist − halfdiag > max_range` → мимо,
  где `halfdiag = 0.5 · cube · √3` — полудиагональ куба (`:292`);
- **полупространство**: `dz = axis · d ≤ 0` → куб за камерой;
- **конус**: при `--max-view-angle < 180°` требуется
  `dz / max(dist, ε) ≥ cos_view − margin`, где
  `margin = halfdiag / max(dist, halfdiag)` — запас на размер куба, чтобы
  куб, задевающий конус краем, не был отброшен.

Результат — список `seen` (индексы кубов). Это грубый отбор: он лишь уменьшает
объём работы, точные гейты применяются к точкам на этапах 4 и 5.

## Этап 4. Z-буфер окклюзии кадра

`cube_colourise.cpp:338‑372`. Сначала по всем точкам кубов `seen` заполняется
сетка минимальной глубины `zmin[cell] = min(pc.z)` с шагом
`--occlusion-cell` px, затем точка отбрасывается, если
`pc.z > zmin[cell] + --occlusion-depth-tol` — она закрыта другой поверхностью.

Два важных решения:

- **точка проекции в сетке** — `iu / cell`, `iv / cell`, `gw = ceil(width/cell)`;
- **приватные сетки на поток**: заполнять одну общую сетку из потоков нельзя —
  `if (z < zmin[c]) zmin[c] = z;` — это гонка, теряющая обновления, и результат
  становится недетерминированным. Поэтому у каждого потока своя сетка
  (`grid_thread`), а слияние идёт по номеру потока (`:367‑371`) — детерминированно.

Внутри обоих проходов (z-буфер и скоринг) применяются точные гейты:
`pc.z > 1e-6`, `|pc| ≥ --min-camera-dist`, `pc.z / |pc| ≥ cos(max_view_angle)`,
проекция `Proj::operator()` (`:107‑118`, та же арифметика radtan, что в
`projectPinhole` из `project.cpp:30`) и попадание в кадр
`i = nearbyint(u) ∈ [0, width)`, `j = nearbyint(v) ∈ [0, height)`.

Окклюзию стоит держать включённой: без неё «прозрачные для порядка» поверхности
(заборы, стволы) окрашиваются с невидимой стороны. Практические параметры из
памяти проекта — `--occlusion-cell 1 --occlusion-depth-tol 0.03`.

## Этап 5. Скоринг и выбор кадра для точки

`cube_colourise.cpp:374‑425`, параллельно по кубам с динамической балансировкой
(блоки по 64 куба, `parallelDynamic`, `:39‑62` — кубы разной плотности, при
статическом разбиении часть ядер простаивала).

Для точки `j` с временем `q.t` и кадром-кандидатом:

```
term_t = w_t · |t_photo − q.t| / T_ref          (w_t = --score-time-weight,
                                                 T_ref = --score-time-scale)
score  = term_t + w_d · min(1, d / D_ref)       (w_d = --score-dist-weight,
                                                 D_ref = --score-dist-scale)
```

- **раннее отсечение**: если `term_t ≥ best[j]`, точка пропускается без
  проекции. Это *точное* отсечение, а не эвристика: второй член неотрицателен,
  поэтому `score ≥ term_t`; `best[j]` хранит текущий лучший балл точки
  (`vector<float>`, `:281`).
- при меньшем балле запоминается кадр (`--debug1`: `dbg_photo[j] = fr.pi`),
  сэмплируется BGR и упаковывается цвет
  `rgb = (R << 16) | (G << 8) | B`, `has[j] = 1`.
- масштабирование пикселя при несовпадении размера картинки и `camera.width/height`
  есть: `u_img = nearbyint(u · img.cols / width)`, затем клип к границам.

Цвет точки — от **одного** кадра; усреднения по кадрам в этом режиме нет
(именно это устраняет «просвечивание» тонких стен).

## Этап 6. Запись результата

`saveLasPacked7`, `src/colorise/src/io.cpp:1020` — LAS 1.4 **point format 7**
(36 Б на запись): `X/Y/Z` (int32, исходные), `intensity` (uint16),
`gps_time` (double), RGB = `v · 257`. Порядок точек — пространственный (куб за
кубом), а не исходный. Bounding box и число записей считаются двумя проходами по
`keep`/`pts` без массива индексов (на 56 млн точек это ~450 МБ экономии), запись
проверяется после каждого блока — при переполнении диска файл раньше молча
обрезался.

`--keep-uncolored` пишет и неокрашенные точки (чёрные), иначе они не попадают в
выход.

## Этап 7. `--debug1`: кто дал цвет

`cube_colourise.cpp:456‑510`. При включённой опции в проходе 5 хранится индекс
кадра-победителя (+4 Б на точку), а после записи LAS формируется CSV:

```
# photo 0 = <имя файла>
point,gps_time,photo,dt,dist,score
```

где `point` — номер точки в выходном LAS (порядок совпадает со строками CSV),
`dt = |t_photo − t_point|`, `dist` — расстояние камера→точка, `score` —
пересчитанный балл. Колонка `point` обязательна: в реальных картах `gps_time`
квантован (~0.09 с) и одно значение имеют сотни точек, поэтому по времени точку
однозначно не идентифицировать.

## Детерминизм и память (инварианты, которые нельзя потерять)

- `--jobs 1` и `--jobs N` дают побайтово одинаковый LAS и одинаковый CSV:
  точки принадлежат ровно одному кубу, каждый поток пишет только свои кубы,
  сетки z-буфера приватные и сливаются по номеру потока, порядок записи задан
  сортировкой ключей кубов.
- память: `LasPacked` — 24 Б/точка + накопители `best/out/has` (4+4+1 Б) +
  `--debug1` (+4 Б). На карте 56 154 407 точек пик RSS ≈ 1.97 ГБ против ~20 ГБ
  кадрового конвейера.
- `gps_time`, координаты и `intensity` выхода равны входным (bit-exact);
  порядок точек при этом меняется на пространственный — это ожидаемо и
  документируется.
- параллелизм не меняет **ни одну** строку лога: счётчики `updates`/`uniq`
  агрегируются атомарно, но печатаются после завершения кадра.
