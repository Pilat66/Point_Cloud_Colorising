# Форматы данных

Здесь собрано всё, что нужно знать о входах и выходе кубового режима, включая
подводные камни бинарных полей LAS. Код-источник: `src/colorise/src/io.cpp`
(чтение/запись), `src/colorise/src/trajectory.cpp` (позы).

## 1. Карта (`--cloud`) — LAS с временем точки

Кубовому режиму нужен **`gps_time` у каждой точки**, поэтому подходит только
`.las`. PCD прочитается для кадрового режима, но в кубовом упадёт с ошибкой
`cube mode needs a LAS with gps_time`.

Читает `streamLasRaw` (`io.cpp:884`), свои читатели, без внешних библиотек:

| Что | Как |
|---|---|
| Сигнатура | `LASF` в первых 4 байтах, `header_size ≥ 227`, `point_data_offset ≠ 0` |
| Версия | LAS 1.0–1.4 (читается номер версии, но не ограничивает) |
| Форматы точек | `0…10` (маска `h[104] & 0x0F`); `> 10` — ошибка |
| Сжатие | `.laz` отвергается (бит `0x20` в `h[104]`) — распакуйте `laszip` |
| Число точек | legacy-счётчик `h+107`, при нуле — 64-битный счётчик `h+247` (LAS 1.4) |
| scale/offset | `h+131..171` (`sx,sy,sz,ox,oy,oz`), применяются как `x = sx·X + ox` |
| Длина записи | `rec_len` из `h+105`; время читается только если `rec_len ≥ t_off + 8` |
| Точки | чанками (`streamLasRaw(path, meta, cb, chunk_records)`, по умолчанию 1 048 576 записей) |

**Смещение `gps_time`** — `lasTimeOffset` (`io.cpp:879`):

| Форматы | Смещение | Примечание |
|---|---|---|
| 0, 2 | — | времени нет, кубовый режим не заработает |
| 1, 3, 4, 5 | 20 | классические форматы с GPS time |
| 6, 7, 8, 9, 10 | 22 | LAS 1.4 |

**Важно про RGB.** В формате 7 RGB занимает байты **30–35**, а сканирование
записи выполняется по `rec_len` из заголовка. Если писать RGB по смещению 28
(как в формате 3), будут затираться младшие байты `gps_time` — в результате
получаются NaN вместо времени. Проверяйте пару (формат, смещение), когда
генерируете входной LAS самостоятельно.

Точки отдаются как **исходные** int32 `X/Y/Z`, `intensity` (uint16) и `double`
время — именно в таком виде они кладутся в `LasPacked` и потом попадают в выход,
поэтому координаты/интенсивность/время переносятся bit-exact.

## 2. Траектория (`--trajectory`)

`loadTrajectory` (`trajectory.cpp:152`):

- разделитель определяется по первой строке: `;` (если их не меньше, чем `,`)
  или `,`;
- заголовок распознаётся, если первая колонка `time|stamp|t|timestamp`;
- **8 и больше колонок** → трактуется как кватернион:
  `t, x, y, z, qx, qy, qz, qw` (кватернион нормализуется);
- **7 колонок** → углы Эйлера: `t, x, y, z, roll, pitch, yaw`,
  порядок `--euler-order {xyz|zyx}`;
- единицы углов: `--euler-units auto` — если 90-й перцентиль модуля углов
  меньше π, считаются радианами, иначе градусами; можно задать явно `deg|rad`;
- `--time-shift <s>` прибавляется ко всем временам (компенсация сдвига часов);
- строки сортируются по времени; нужно не меньше двух пригодных строк.

Поза на время снимка: линейная интерполяция позиции + SLERP кватерниона
(`Trajectory::sampleAt`, `trajectory.cpp:98`).

## 3. Калибровка (`--calib`)

Один JSON-файл на всё: интринсики **и** экстраинсик (отдельный `camera.yaml` не
читается). Интринсики ищутся в любом объекте дерева, у которого есть признаки
камеры (`intrinsics|K|camera_matrix|fx|cam_fx`); приоритет — ключ `camera`,
затем `camera*`, затем `cam*` (`io.cpp:185‑196`).

```json
{
  "camera": {
    "camera_model": "plumb_bob",
    "width": 1600, "height": 1300,
    "intrinsics": [fx, fy, cx, cy],
    "distortion_coeffs": [k1, k2, p1, p2, k3]
  },
  "results": { "T_lidar_camera": [x, y, z, qx, qy, qz, qw] }
}
```

| Поле | Принимаемые ключи |
|---|---|
| Модель | `camera_model` / `model` / `distortion_model` / `cam_model`; `fish`/`equidistant` → fisheye, остальное → pinhole |
| Размер кадра | `width`/`height` (обязательны), также `image_width`/`image_height`, `cam_width`/`cam_height` |
| Интринсики | `intrinsics` `[fx,fy,cx,cy]`, либо `K`/`camera_matrix` (3×3), либо `fx,fy,cx,cy` (`cam_fx..`) |
| Дисторсия | `distortion_coeffs`, `dist_coeffs`, `D` (любая длина) или `cam_d0…cam_d5` |

Экстраинсик ищется по всему дереву по именам `T_camera_lidar`, `T_lidar_camera`,
`T_lidar_cam`, `T_cam_lidar` (`io.cpp:157‑162`); явное имя задаётся
`--extrinsic-name results.T_lidar_camera` (сравнение по суффиксу пути).
Поддерживаемые представления: 7 чисел `x,y,z,qx,qy,qz,qw`; 4×4; 12 чисел
(R + t); объект `{translation + rotation/quaternion}`.

**Направление.** Ключ с `lidar_camera` означает «world/lidar from camera» и
автоматически инвертируется, ключ с `camera_lidar` применяется как есть.
Схема именования — `A_from_B`. Принудительно:
`--extrinsic-direction camera_from_lidar|lidar_from_camera`.
Внутри режима используется `T_lidar_cam` («camera from lidar»).

## 4. Снимки (`--photos`)

`listPhotos` (`io.cpp:1097`): берутся регулярные файлы с расширениями
`jpg/jpeg/png/bmp`. Время съёмки — из имени (без расширения):

- имя целиком цифровое → число разбирается как время;
- иначе берётся **самая длинная цифровая группа** (например
  `IMAGE_1789476925898092722.jpg`);
- единицы: `≥ 1e15` — наносекунды, `≥ 1e11` — миллисекунды, иначе секунды
  (`photoTimestampFromName`, `io.cpp:1076`).

Список сортируется по времени; в кадры попадают снимки, чьё время укладывается
в интервал траектории ± `--time-tolerance` (иначе они пропускаются, в логе
видно `[frames] N usable of M photos`).

## 5. Выход (`--output`) — LAS 1.4 point format 7

`saveLasPacked7` (`io.cpp:1020`) пишет заголовок 375 Б и записи по 36 Б:

| Смещение | Поле |
|---|---|
| 0, 4, 8 | `X`, `Y`, `Z` — int32, исходные значения входа |
| 12 | `intensity` — uint16, исходная |
| 14 | return bits = `0x11` (первый из одного) |
| 16, 17 | classification = 0, user data = 0 |
| 18, 20 | scan angle = 0, point source id = 0 |
| 22 | `gps_time` — double, исходное значение |
| 30, 32, 34 | `R`, `G`, `B` — uint16, `v · 257` (8-битный канал, растянутый в 16 бит) |

scale/offset в заголовке выхода **совпадают с входными**, RGB и время
записываются как есть, поэтому повторное чтение даёт те же координаты с
точностью кванта 0.001 м. Порядок точек — пространственный (по кубам), не
исходный.

При `--keep-uncolored` в файл попадают все точки (неокрашенные — с чёрным
цветом), иначе только окрашенные.

## 6. `--debug1` — CSV «какой кадр дал цвет какой точке»

```
# photo 0 = 1789476708485542797.png
# photo 1 = 1789476709685605461.png
point,gps_time,photo,dt,dist,score
0,1789476853.310546875,19,15.617539,2.021521,15.819690997
```

- `point` — номер точки в **выходном** LAS (порядок строк совпадает с порядком
  точек в файле);
- `gps_time` — время точки (как в LAS);
- `photo` — индекс кадра в списке снимков (легенда `# photo N = имя файла`);
- `dt = |t_photo − t_point|`, `dist` — расстояние камера→точка,
  `score` — пересчитанный балл.

Строки пишутся только для окрашенных точек. Идентифицировать точку по одному
`gps_time` нельзя: в реальных картах время квантовано (~0.09 с) и одно значение
делят сотни точек.

## 7. Соглашения об упаковке и округлении

| Где | Формат |
|---|---|
| PCD `rgb` | `uint32`, `(R << 16) \| (G << 8) \| B` (PCL-соглашение) |
| LAS RGB | 8-битные каналы как `v · 257` |
| Округление пикселей/каналов | half-to-even (`std::nearbyint`) |
| Глубина в z-буфере | float от `pc.z` (double) |
