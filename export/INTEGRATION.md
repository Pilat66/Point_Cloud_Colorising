# Встраивание в другой проект (пример: `FAST-LIVO2-LAS`)

Возможны три уровня переноса — от «ничего не менять» до «встроить как функцию».
Ниже сначала минимальный путь (уровень 1) на конкретных артефактах
`FAST-LIVO2-LAS`, затем что заменять при более глубокой интеграции.

## 1. Точки стыковки с `FAST-LIVO2-LAS`

Проверено по их коду и данным:

| Нужно нам | Что есть у них | Совместимость |
|---|---|---|
| LAS с `gps_time` | `data/las/<run>/all_raw_points.las` — LAS 1.4 fmt 7, время пер-точечно (`fast_livo_las/include/utils/las_writer.h`, `src/las_writer.cpp`) | читается без конвертации: fmt 7 → время по смещению 22 |
| `trajectory.csv` | `<lasPath>/trajectory.csv`, заголовок `time;x;y;z;roll;pitch;yaw` (`LIVMapper::saveTrajectoryCsv`, `LIVMapper.cpp:264‑288`) | формат совпадает с нашим (7 колонок, `;`, Эйлер); время — штамп IMU, единицы определяются автоматически |
| Каталог снимков | `ImageCleaner` (`image_hash.py` / `cpp/build/image_cleaner`) в режиме `--export` пишет `<header stamp ns>.jpg`; в их README прямо указано, что такая папка годится как `--photos` для нашего `ColoriseMap` | имя = наносекунды → `photoTimestampFromName` разбирает (≥1e15 → ns) |
| `calib.json` | интринсики в `fast_livo_las/config/camera_*.yaml`, экстраинсик `extrin_calib.extrinsic_R/extrinsic_T` | нужен разовый переходник (§2) |
| Формат выхода | их новый `LASWriter` пишет **тот же** LAS 1.4 fmt 7 (36 Б/точка, RGB×257, `gps_time`, commit «LAS Point Format 7 (RGB)») | выход нашего режима читается их инструментами, и наоборот |

Итого: на их артефактах наш режим запускается без единой правки кода — нужен
только `calib.json`.

## 2. `calib.json`: разовый переходник из их YAML

Берём интринсики из их `camera_*.yaml` (или `mid360_right.yaml`) и экстраинсик из
`extrin_calib` того конфига, с которым строилась карта:

```json
{
  "camera": {
    "camera_model": "pinhole",
    "width": 1600,
    "height": 1300,
    "intrinsics": [fx, fy, cx, cy],
    "distortion_coeffs": [k1, k2, p1, p2, k3]
  },
  "results": {
    "T_camera_lidar": [tx, ty, tz, qx, qy, qz, qw]
  }
}
```

Соответствие полей:

| Их ключ | Наш ключ | Примечание |
|---|---|---|
| `image_width`/`image_height` (или размер кадра) | `camera.width` / `camera.height` | обязательны, иначе остановка с ошибкой |
| `intrinsic_matrix` / `fx,fy,cx,cy` (`camera_*.yaml`) | `camera.intrinsics = [fx,fy,cx,cy]` | принимается и `K` (3×3) |
| `distortion_coefficients` / `D` | `camera.distortion_coeffs` | длина любая |
| `extrin_calib.extrinsic_T` | часть `T_camera_lidar` (t) | их конвенция `Rcl`/`Pcl` = **camera from lidar** |
| `extrin_calib.extrinsic_R` (9 чисел, row-major) | часть `T_camera_lidar` (R) | можно писать 12 числами: 9 R построчно + 3 t |

Если удобнее не конвертировать R в кватернион — формат `12 чисел` избавляет от
этой арифметики: `"T_camera_lidar": [R11,R12,R13,R21,R22,R23,R31,R32,R33,tx,ty,tz]`.
Ключ `T_camera_lidar` берётся как есть; если назвать ключ
`T_lidar_camera`, наш загрузчик сам инвертирует матрицу. При сомнениях —
`--extrinsic-direction`.

## 3. Запуск на их артефактах

```bash
colorise_map --cube 1.0 \
    --cloud      data/las/<run>/all_raw_points.las \
    --photos     <out>/img-uniq-filtered \
    --trajectory data/las/<run>/trajectory.csv \
    --calib      calib.json \
    --min-camera-dist 0.5 --map-max-range 0 \
    --occlusion-cell 1 --occlusion-depth-tol 0.03 \
    --keep-uncolored --debug1 colored-debug1.csv \
    --output     colored.las
```

`--occlusion-cell 1` и `--occlusion-depth-tol 0.03` — параметры из практики
этого режима (заметно чище стволы/заборы, чем 4 px и 0.3 м).

## 4. Разовые проверки стыков

1. **Тайм-база.** Смотрите две строки лога:
   `[trajectory] N poses t=[a, b]` и `[photos] M t=[c, d]`. Интервалы должны
   пересекаться; иначе появится `[WARN] photo times ... do not overlap`, а
   `[frames] 0 usable` приведёт к ошибке. Правится `--time-shift`, крайние
   снимки — `--time-tolerance`.
   Точная проверка после прогона: в `--debug1` колонка `dt` должна быть порядка
   половины интервала между кадрами (для 5–10 Гц это ≤ 0.2 с). Если `dt`
   порядка `1e9` — снимки и траектория в разных единицах времени.
2. **Экстраинсик.** Прогон с `--map-max-range 0 --keep-uncolored` и взгляд на
   `==== RESULT ====`: при верном экстраинсике доля `coloured` — десятки
   процентов. Ошибка знака/порядка осей даёт единицы процентов или цвет,
   «съезжающий» с геометрии; быстрая визуальная проверка — PCDViewer,
   CloudCompare, Easy3D.
3. **Детерминизм.** `--jobs 1` и `--jobs 0` (авто) → `cmp` двух LAS и `diff`
   двух `--debug1` CSV. Расхождение = потерян инвариант приватных z-буферов.
4. **Перенос полей.** Через laspy: множества/суммы `gps_time` входа и выхода,
   совпадение scale/offset, число точек = числу окрашенных (или всех при
   `--keep-uncolored`); RGB выхода — 8-битные каналы, растянутые `×257`.

## 5. Что заменять при более глубокой интеграции

| Наше | Заменить на | Требования к замене |
|---|---|---|
| `streamLasRaw` (`io.cpp:884`) | чтение LAS хост-проекта (PCL+laszip, свой reader) | **потоковость**: точки должны отдаваться чанками — иначе исчезнет главный выигрыш по памяти (на 15 млн точек `LasPacked` = 360 МБ, а «сырые» массивы + упаковка = втрое больше) |
| `saveLasPacked7` (`io.cpp:1020`) | `LASWriter::addPointRgb` в `FAST-LIVO2-LAS` | перенести проверку ошибок записи (в исходном коде этого режима она появилась после случая с молча обрезанным файлом) |
| `loadTrajectory` / `Trajectory::sampleAt` (`trajectory.cpp:152`, `:98`) | свой источник поз (у них позы уже есть в `LIVMapper`) | сохранить интерполяцию на время кадра (линейно + SLERP) и `T_lidar_cam` из калибровки |
| `loadCameraFromCalib` / `loadCalib` (`io.cpp:233`, `:328`) | своя конфигурация (YAML) | нужны: модель (pinhole), `width`/`height`, `fx,fy,cx,cy`, дисторсия, `T_lidar_cam` |
| `listPhotos` (`io.cpp:1097`) | ROS-кадры напрямую (`cv_bridge`/`image_transport`) | в кубовом режиме картинка нужна целиком, поэтому распаковка должна быть на кадр, а не на точку |
| `cubeKey` (`cube_colourise.cpp:123`) | то же, при необходимости с другим числом бит | 21 бит на ось ≈ ±1 км при кубе 1 м; для больших сцен расширять или переводить на двойной ключ |

## 6. Инварианты, которые нельзя потерять

1. **Детерминизм**: `--jobs 1` == `--jobs N` (побайтово). Обеспечивается тем, что
   точка принадлежит ровно одному кубу, каждый поток пишет только свои кубы, а
   сетки z-буфера приватные и сливаются по номеру потока.
2. **Bit-exact перенос**: `gps_time`, int32-координаты и `intensity` выхода
   равны входным; scale/offset не меняются. Проверяется сверкой множеств времён.
3. **Порядок точек** — пространственный (по кубам), а не исходный: любой
   потребитель, ожидающий исходный порядок, должен это учитывать.
4. **Память**: никаких массивов размером с карту, кроме `LasPacked`
   (24 Б/точка) и накопителей; z-буфер и списки кубов зависят от кадра, а не от
   карты.
5. **Раннее отсечение по времени точное**: `score ≥ term_t`, поэтому отбрасывать
   кандидата при `term_t ≥ best` можно без потери качества. Если менять формулу
   балла (например, делать член расстояния ненасыщающимся), отсечение перестанет
   быть корректным.

## 7. Ограничения режима (и что из-за них проверить при внедрении)

- **только pinhole** — fisheye падает с внятной ошибкой (`cube_colourise.cpp:157`);
- **одна камера** на прогон (`main.cpp:775‑779`: `--cube works with exactly one camera`).
  Мультикамерность — это отдельная доработка (в кадровом режиме она есть: пары
  кадров подбираются по `--max-time-offset`);
- **вход только LAS с временем** — PCD, `.laz`, форматы 0/2 не подходят;
- цвет — **от одного кадра**, усреднения нет: на стыках кадров возможны
  «швы» по цвету; если это критично, нужен вариант с усреднением (в кадровом
  конвейере он есть — `csum/ccnt` и `--min-color-frames`);
- **`--debug1` только с `--cube`** и добавляет 4 Б/точку.

## 8. Что осталось за пределами экспорта

В репозитории-источнике есть ещё кадровый режим того же приложения (усреднение
по кадрам, радиусный отбор `VoxelGrid`, `--nearest-wins`) и отдельный скановый
инструмент `colorise/` — они в экспорт не попали намеренно, чтобы набор решал
одну задачу. При необходимости их можно вынести так же: `docs/` содержит
описание проекционного ядра, которое у них общее с кубовым режимом
(`projectAndSample` в `src/colorise/src/project.cpp:56`).
