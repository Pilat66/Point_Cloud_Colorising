# colorise_offline — C++ порт colorise_offline.py

Standalone-раскраска облака точек по набору фотографий с временными метками и
файлу траектории лидара. Это ROS-free C++ реализация того же конвейера, что и
`colorise_offline.py` (проекционное ядро `projectAndSample`): гейты по
дистанции/углу/краю, проекция камеры (pinhole/fisheye), z-буфер окклюзии,
усреднение цвета по кадрам.

Валидация: на реальных данных репозитория (облако `1788882799423559018.pcd`,
1 201 612 точек, 82 кадра) выходные PCD-файлы C++ и Python совпадают
**побайтово**; логи по кадрам (`coloured`/`cand`/`uniq_so_far`) идентичны.
Для `.las` входов выход тоже побайтово совпадает с Python (`laspy`) — проверено
на LAS 1.2 форматов 0/1/3 и LAS 1.4 формата 6.
LAS-выход проверен чтением через `laspy`: совпадают число точек, координаты
(в пределах 0.5 мм квантования), интенсивность и RGB (`×257`), а также
min/max-бокс в заголовке; пустая выборка даёт валидный LAS с 0 точек.

---

## 1. Зависимости

Только системные пакеты:

| Библиотека | Для чего |
|---|---|
| Eigen3 ≥ 3.3 | 4×4-трансформы, кватернионы, SLERP |
| OpenCV ≥ 4 | чтение фото (и проекция fisheye/сложной дисторсии) |
| nlohmann/json | vendored single-header в `third_party/nlohmann/` (не нужен в системе) |

```bash
sudo apt install libeigen3-dev libopencv-dev
```

## 2. Сборка

```bash
cd colorise
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j4
```

Получается бинарник `build/colorise_offline`.

## 3. Быстрый старт

Из корня репозитория (в `data/` лежат примеры):

```bash
./colorise/build/colorise_offline \
    --cloud data/all_raw_points.pcd \
    --photos data \
    --trajectory data/trajectory.csv \
    --calib data/calib.json \
    --output coloured.pcd
```

Все аргументы имеют те же значения по умолчанию, что и в Python-версии:

```bash
./colorise/build/colorise_offline
```

## 4. Входные данные

| Аргумент | По умолчанию | Что это |
|---|---|---|

### 4.1 Фотографии

Время снимка берётся из имени файла — эпоха в наносекундах:
`1788882722018994333.png` → `1788882722.018994333` с. Поддерживаются
`.jpg/.jpeg/.png/.bmp`; допускаются имена вида `IMAGE_<ts>.jpg` (берётся самая
длинная цифровая группа). Единицы определяются автоматически:
`≥1e15` — наносекунды, `≥1e11` — миллисекунды, иначе — секунды.

### 4.2 Траектория (`trajectory.csv`)

Два формата, разделитель `;` или `,` определяется автоматически:

```text
time;x;y;z;roll;pitch;yaw            # 7 колонок, углы Эйлера
time,x,y,z,qx,qy,qz,qw               # 8 колонок, кватернион
```

Для углов Эйлера: `--euler-units auto|deg|rad` (автоопределение по 90-му
перцентилю величины углов) и `--euler-order xyz|zyx` (`xyz` = `Rz·Ry·Rx`).
Поза лидара интерполируется на момент снимка (линейно по позиции, SLERP по
кватерниону); снимок вне диапазона траектории зажимается к ближайшему концу,
если он не дальше `--time-tolerance`, иначе кадр пропускается.

### 4.3 Камера (блок `camera` в `calib.json`)

Интринсики, дисторсия и размер кадра берутся из блока `camera` того же
`--calib`, что и экстраинсик — отдельный `camera.yaml` не читается:

```json
{
  "camera": {
    "camera_model": "plumb_bob",
    "width": 1600,
    "height": 1300,
    "intrinsics": [915.9333861, 916.9603583, 786.2636665, 643.6658678],
    "distortion_coeffs": [0.05847161997, -0.08154755066, -0.001797524801,
                          -0.003098832848, 0.01941807927]
  },
  "results": { "T_lidar_camera": [x, y, z, qx, qy, qz, qw] }
}
```

Распознаваемые ключи блока (первый найденный выигрывает):

| Что | Ключи |
|---|---|
| Модель | `camera_model` / `model` / `distortion_model` / `cam_model`: `plumb_bob`, `pinhole`, `radtan` → pinhole; `fisheye`, `equidistant` → fisheye |
| Размер кадра | `width`/`height` (обязательны), также принимаются `image_width`/`image_height`, `cam_width`/`cam_height` |
| Интринсики | `intrinsics`: `[fx,fy,cx,cy]`; либо `K`/`camera_matrix` (3×3); либо `fx/fy/cx/cy` (или `cam_fx..cam_cy`) |
| Дисторсия | `distortion_coeffs`, `dist_coeffs`, `D` (любая длина) или `cam_d0..cam_d5` |

Образец формата — `data/calib-pinhole-2026-09-16.json` (свежая калибровка
камеры набора «пруд Голубое»). Если блока `camera` нет или в нём нет
`width`/`height`, прогон останавливается с внятной ошибкой — «молчаливого»
размера по умолчанию больше нет.

`cam_d0..cam_d5` либо `distortion_coeffs`; ключи `width/height/fx/fy/cx/cy`
тоже поддержаны. Fisheye включается по `fish`/`equidistant` в имени модели.

### 4.4 Экстраинсики (`calib.json`)

Нужная матрица ищется по всему JSON-дереву по ключам
`T_camera_lidar` / `T_lidar_camera` / `T_lidar_cam` / `T_cam_lidar` (или явно:
`--extrinsic-name results.T_lidar_camera`). Поддерживаемые представления:
7 чисел `x,y,z,qx,qy,qz,qw`, 4×4, 12 чисел (R+t), объект
`{translation + rotation/quaternion}`. Направление определяется по имени ключа
(`...lidar_camera...` инвертируется) и может быть принудительно задано через
`--extrinsic-direction camera_from_lidar|lidar_from_camera`.

### 4.5 Облако (`--cloud`)

Два формата:

- **`.pcd`** — бинарный, поля `x y z [nx ny nz] intensity [curvature …]`
  (`SIZE` и `TYPE` из заголовка уважаются);
- **`.las`** — несжатый LAS 1.0–1.4, форматы записей 0–10 (собственный
  читатель, без `laspy` и иных библиотек). Читаются масштабированные X/Y/Z
  (`scale`/`offset` из заголовка) и `intensity` (uint16, есть во всех
  форматах). Сжатый `.laz` не поддерживается — распакуйте через `laszip`
  (Python-версия без laszip-бэкенда тоже его не читает).

### 5.1 Окклюзия: механика и что меняет `--occlusion-cell`

Z-буфер (`Pass 3` в `colorise/src/project.cpp`, те же строки в
`src/colorise.cpp` и `project_and_sample()` в Python-версии):

1. кадр делится на сетку ячеек `cell = max(1.0, --occlusion-cell)` px:
   `ceil(width/cell) × ceil(height/cell)` (пиксельные координаты округлены до
   целых ещё до z-буфера, поэтому `cell=1` — это сетка ровно в пиксель);
2. в ячейке запоминается **минимальная глубина** — координата `z` в системе
   камеры, не дальность — среди спроецированных в неё точек;
3. точка остаётся, только если `depth <= zmin_ячейки + --occlusion-depth-tol`.

Ячейка — это квантование z-буфера: все точки, попавшие в одну ячейку, делят
один `zmin`. Отсюда главное свойство: **чем больше ячейка, тем строже
отбраковка**, и строго монотонно — всё, что выжило при крупной ячейке, выжило и
при мелкой (`kept(cell) ⊆ kept(1)`; точки, окрашенной только при крупном
`cell`, не появилось ни в одном прогоне). `cell=1` сохраняет максимум
наблюдений, значения `<1` приводятся к `1`.

| `--occlusion-cell` | Что происходит | Потеря наблюдений против `cell=1` |
|---|---|---|
| `1` | точный z-буфер: точка гасится, только если в **её собственный пиксель** спроецировалась более близкая точка. Максимум наблюдений; основную работу делает сам z-буфер (81.3 % кадра без окклюзии → 77.6 %). У контуров цвет может «протечь» на соседние пиксели | 0 % |
| `4` (по умолчанию) | ячейка 4×4 px: близкая точка затеняет всю площадку, то есть дополнительно срезает протечки у контуров | 4.4 % |
| `8`–`16` | строже: контуры чище, но растут пропуски на наклонных и разреженных поверхностях | 8.8–18.9 % |
| `32`–`64` | агрессивно: в одну ячейку попадают близкие и дальние куски (земля, крыша, стена), дальние теряют наблюдение | 37–63 % |
| `128` и выше | на кадр остаётся 1–4 ячейки (при `1024` и кадре 1600×1300 — ровно 4): выживает лишь то, что ближе `zmin + tol` | 82 % и больше (при `1024` окрашено 0.5 % наблюдений) |

Замеры ниже — облако `1788882799423559018.pcd` (1 201 612 точек),
`data/calib.json` (блок `camera`, 1600×1300), гейты по умолчанию (`--max-range 20`,
`--min-camera-dist 2`, `--max-view-angle 75`), `--occlusion-depth-tol 0.3`.
Одиночный кадр — `data/1788882849226457611.png`, 977 398 точек после гейтов;
значения воспроизводятся в C++ и в Python **число в число**.

|---:|---:|---:|---:|
| `1` | 931 853 | — | — |
| `2` | 914 004 | 17 849 | 1.9 % |
| `4` | 890 688 | 41 165 | 4.4 % |

| `32` | 584 058 | 347 795 | 37.3 % |

Прогон по 82 кадрам (то же облако и те же кадры, режим усреднения). «Наблюдений
сохранено» — `Σ coloured / Σ cand` по всем кадрам:

| `--occlusion-cell` | coloured всего | покрытие | наблюдений сохранено |
|---|---:|---:|---:|
| выкл. (`--no-occlusion`) | 1 196 924 | 99.61 % | 82.6 % |
| `1` | 1 196 874 | 99.61 % | 77.3 % |
| `4` | 1 196 386 | 99.57 % | 72.3 % |
| `8` | 1 195 276 | 99.47 % | 67.7 % |
| `16` | 1 191 194 | 99.13 % | 59.2 % |
| `32` | 1 182 868 | 98.44 % | 46.7 % |
| `64` | 1 143 370 | 95.15 % | 31.0 % |
| `128` | 954 031 | 79.40 % | 15.9 % |
| `256` | 631 295 | 52.54 % | 5.9 % |
| `1024` | 143 180 | 11.92 % | 1.3 % |

Отсюда практический вывод: на многофреймовом прогоне **итоговое покрытие почти
не чувствительно к ячейке** — потерянное наблюдение точки компенсируется другим
кадром (до `cell=32` разница с `cell=1` не превышает 1.2 п.п. покрытия). Ячейка
решает, какие наблюдения попадут в усреднение: больше ячейка ⇒ меньше протечек,
но и меньше наблюдений на точку (усреднение менее устойчиво), а дырки в
покрытии начинаются примерно с `cell≈64` и становятся катастрофическими при
128 и выше. Одиночный кадр компенсировать нечем: 81.3 % без окклюзии → 77.6 %
(`1`) → 74.1 % (`4`) → 62.9 % (`16`) → 29.0 % (`64`) → 0.5 % (`1024`).

Насколько это видно в цвете (тот же прогон по 82 кадрам, усреднение):

| Сравнение | точки, окрашенные в обоих | средний сдвиг RGB | меняют цвет >10 из 255 | >30 | теряют цвет |
|---|---:|---:|---:|---:|---:|
| `--no-occlusion` → `cell=4` | 1 196 384 | 3.4 | 10.9 % | 1.6 % | 538 |
| `cell=1` → `cell=4` | 1 196 384 | 1.8 | 3.7 % | 0.6 % | 488 |
| `cell=4` → `cell=32` | 1 182 852 | 4.6 | 15.2 % | 1.2 % | 13 518 |
| `cell=4` → `cell=128` | 954 026 | 11.6 | 47.7 % | 8.5 % | 242 355 |

То есть 82-кадровый прогон без окклюзии отличается от дефолта заметно лишь на
~11 % точек, а переход `cell=1 → 4` трогает единицы процентов: дефолт `4.0`
стоит на «пологом» участке кривой. Грубые ячейки (`128` и выше) меняют цвет
уже у половины облака, поэтому такие значения — не тюнинг, а осознанное
решение.

Взаимодействие с `--occlusion-depth-tol`: ячейка решает, насколько «широко»
близкая поверхность затеняет соседей, а допуск — какая разница глубин внутри
ячейки считается одной поверхностью. Больше ячейка — строже, больше допуск —
мягче. На наклонных поверхностях (земля, крыша) разброс глубин внутри крупной
ячейки растёт быстро; если цель — сохранить плоскость, крупную ячейку имеет
смысл брать только вместе с увеличенным `--occlusion-depth-tol`.

Стоимость: z-буфер это `ceil(w/cell) × ceil(h/cell)` ячеек (при 1600×1300 —
2.08 млн ячеек / 16.6 МБ при `cell=1`, 130 тыс. / 1.0 МБ при `4`, 4 ячейки при
`1024`), а время прогона меняется слабо — доминируют проекция и чтение фото
(4.2–6.1 с на 1.2 млн точек × 82 кадра при `--jobs 8`; крупные ячейки чуть
быстрее, разница на уровне шума). Смотреть эффект проще всего по строке кадра:
`coloured=` против `cand=` — например, на кадре 82 без окклюзии
`coloured=1 080 808`, при `cell=4` — `803 014`, при `cell=64` — `302 337`.

## 6. Выход

Формат определяется расширением `--output`:

- **`.pcd`** (и любое другое расширение, как в Python-версии) — бинарный PCD
  `FIELDS x y z intensity rgb`, `TYPE F F F F U`; `rgb` — упакованный `uint32`
  (PCL-соглашение): `(R << 16) | (G << 8) | B`. Байт в байт совпадает
  с Python-версией.
- **`.las`** — несжатый LAS 1.2, формат записи 3 (XYZ + intensity +
  GPS time = 0 + RGB), масштаб 1 мм, offset по минимуму данных. Интенсивность
  округляется к ближайшему целому (half-to-even), 8-битные RGB-компоненты
  пишутся в 16-битные поля LAS как `v * 257` — так цвет корректно выглядит во
  вьюерах, берущих видимый цвет из старшего байта (CloudCompare и т. п.).
  Сжатый `.laz` на выходе не поддерживается (понятная ошибка, exit 1).

В LAS-выход попадают те же точки, что и в PCD: по умолчанию только окрашенные,
а с `--keep-uncolored` — все (неокрашенные чёрные). По умолчанию цвет
усредняется по кадрам, увидевшим точку.

## 7. Отличия от Python-версии

| | Python | C++ |
|---|---|---|
| Радиусное кадрирование | `scipy.spatial.cKDTree` | воксельная сетка (`include/voxel_grid.hpp`), та же семантика `<= r` |
| `.las` вход | да (laspy) | да (свой читатель LAS 1.0-1.4, форматы 0-10; `.laz` — нет) |
| `.las` выход | нет (только PCD) | да, по расширению `--output` (LAS 1.2 формата 3; `.laz` — нет) |
| `--preview` | флаг есть, не используется | нет |
| `--no-occlusion` | нет | добавлен для удобства |
| Скорость (1.2 млн точек, 82 кадра) | ~200 с | ~6 с (8 потоков), ~16 с (`--jobs 1`) |
| Округление | `np.round` (half-to-even) | `std::nearbyint` (half-to-even) |
| Параллелизм | нет | `--jobs N`: кадры обрабатываются concurrently, коммит и лог — строго в порядке кадров (выход и логи совпадают байт в байт с однопоточным прогоном и Python) |
| Строка лога | — | добавляется `[parallel] N worker threads` |

## 8. Типичные проблемы

| Симптом | Причина / решение |
|---|---|
| `coloured=0`, покрытие 0 % | Фото и траектория из разных прогонов (сверить диапазоны `[photos]`/`[trajectory]`, выровнять `--time-shift`) или `--min-color-frames` выше числа кадров |
| «no points within … m» | `--max-range` мал или камера далеко от облака (`--extrinsic-direction`) |
| Цвет «плывёт» по рёбрам | Увеличить `--min-camera-dist`, `--occlusion`, `--min-color-frames` |
| Цвет протекает через контуры: точка за стеной/машиной покрашена цветом переднего плана | Увеличить `--occlusion-cell` (4 → 8/16) или уменьшить `--occlusion-depth-tol` |
| Дырки и пропуски на плоскостях, в кадре окрашено мало точек | Уменьшить `--occlusion-cell` (16 → 4/2/1) или увеличить `--occlusion-depth-tol`; сверить `coloured=` / `cand=` по кадрам (см. §5.1) |
| Проекция «зашумлена» у краёв | Увеличить `--edge-margin`, снизить `--max-view-angle` |
| Выходной `rgb` не совпадает с фото | Проверить направление экстраинсиков и `--euler-order` |

При старте печатается сводка по каждому блоку (`[camera]`, `[extrinsic]`,
`[trajectory]`, `[photos]`, `[cloud]`, `[parallel]`) и строка на кадр — как в
Python-версии. Обработка кадров параллелится на `--jobs` потоков; фиксация
результатов и печать идут строго в порядке кадров, поэтому результат и лог
побайтово совпадают с `python3 colorise_offline.py` с теми же флагами.

Память при параллельной обработке: каждый поток держит декодированное фото,
список кандидатов и результат кадра (~20 МБ при облаке в 1.2 млн точек); при
ограниченной памяти уменьшите `--jobs`.
если он не дальше `--time-tolerance`, иначе кадр пропускается.
